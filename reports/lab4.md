## 第 6 章 文件系统与 I/O

### 1.在我们的easy-fs中，root inode起着什么作用？如果root inode中的内容损坏了，会发生什么？

root inode 是整个目录树的唯一起点，它是 inode 号为 0 的那个 inode。如果 root inode 损坏，最直接的后果是里面的 dirent 读不出来或对不上，此时所有按名字打开文件都会失败，整个文件系统等于不可用。

## 第 7 章 进程间通信

### 1. 举出使用 pipe 的一个实际应用的例子

比如 shell 里的 `|`，`ls -l | grep txt` 就是把左边的输出写进管道，右边的进程再把管道里的内容读出来。具体过程是：shell 先调用 `pipe` 拿到读端和写端两个文件描述符，再 `fork` 出两个子进程，左子进程用 `dup2` 把写端绑到标准输出上再 `exec ls`，右子进程把读端绑到标准输入上再 `exec grep`。这样 `ls` 的输出不再打到终端，而是经由管道成为 `grep` 的输入，两个进程可以一写一读并行流水。内核里的管道是一块共享的环形缓冲区，写满时写者睡眠、有数据时唤醒读者，左边关闭写端后右边读到 EOF 就退出。

### 2. 如何使用 cat 和 wc 完成一个文件的行数统计？

`cat file.txt | wc -l`。`cat` 把文件内容读到用户缓冲区再写到标准输出，shell 建立的管道把它的标准输出接到 `wc` 的标准输入，`wc -l` 统计读到的换行符个数，也就得到了行数。要注意 `wc -l` 数的是换行符，文件末尾若没有换行，最后一行不会计入。

等价写法还有 `wc -l file.txt` 和 `wc -l < file.txt`。前者让 `wc` 自己打开文件、根本不用管道，纯统计行数时它最省事：数据只需从文件系统读一次，而 `cat file | wc -l` 要多走“文件 → cat 缓冲区 → 管道 → wc 缓冲区”两次拷贝，还多起了两个进程。

### 3. 如果需要在多个进程间互相通信，则需要为每一对进程建立一个管道，非常繁琐，请设计一个更易用的多进程通信机制。

把“两两成对的管道”换成“带名字的公共信箱”，也就是**消息队列**。内核维护一张全局消息队列表，用名字或 key 索引：进程用 `msgget(key)` 按名字找到或新建队列并拿到队列 id，发送方用 `msgsnd` 投递一条消息，接收方用 `msgrcv` 取走一条。任意进程只要知道这个名字就能加入同一个队列，于是 N 个进程互通只需要 1 个队列，而不是 N(N-1)/2 个管道，也不必让某个进程充当中转站。

每个队列在内核里是一条环形缓冲加一个等待队列：队列满时 `msgsnd` 阻塞、队列空时 `msgrcv` 阻塞，同步是天然的，不用应用层自己保证。它还把管道那种无边界的字节流变成了有边界的记录——一次发送就是一条完整消息，接收方不必再自己拼接和切分。

另一种可选方案是**共享内存**：共享页帧，映射到所有参与进程的地址空间，设为可读可写，大家一块修改并查看共享内存的信息，数据不必经过内核拷贝，适合大数据量。但共享内存本身不带同步，多个读写者并发访问会产生数据竞争，必须再配一把信号量或互斥锁来保护，实现和使用都比消息队列复杂。一般用消息队列做信令和小数据传递，共享内存只在高吞吐场景下配合锁使用。
